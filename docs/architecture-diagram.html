Split-Plane Architecture

Stateless control plane on Cloud Run, stateful worker agents on GCP Compute with nested KVM.

CONTROL Cloud Run

Stateless Go API. Scales to zero. Handles scheduling, provisioning, config assembly, billing.

Responsibilities

  • REST API for dashboard & CLI
  • Bin-pack scheduling across hosts
  • GCP VM provisioning on demand
  • Config assembly & secret injection
  • Credential encryption & storage
  • Usage tracking & billing

WORKER GCP Compute VMs

Multi-tenant hosts running the Agent process. Each host manages multiple Firecracker MicroVMs.

Components

  • Agent (Go) — VM lifecycle & proxy
  • LiteLLM — shared AI gateway
  • Metadata service — config delivery
  • Persistent disk — data volumes
  • Per-VM Cloudflare tunnels

EDGE Cloudflare

All user traffic enters through Cloudflare. No ports exposed, no public IPs.

Services

  • CF Access — SSO (Google, GitHub, Email)
  • CF Tunnels — per-VM, ephemeral
  • CF Worker — slug-based routing
  • CF KV — route cache (1h TTL)
  • Auto-TLS & custom domains
  • DDoS protection at edge

Firecracker MicroVMs

Each Machine runs in its own KVM-isolated MicroVM with sub-second boot and minimal overhead.

User-defined ports — proxied via agent

Boot Sequence

  • CoW clone of base rootfs (~instant)
  • Create ext4 data volume (sparse, 5GB)
  • Create tap device + bridge IP
  • Boot Firecracker (~125ms)
  • Init script mounts /data, starts services
  • Register per-VM Cloudflare tunnel

Isolation & Storage

Security Boundaries

  • KVM hardware isolation — each VM is a separate kernel
  • Bridge network — 192.168.100.0/24, IP-per-VM
  • Separate rootfs — CoW snapshot, destroyed on stop
  • Memory-only secrets — never written to disk in VM

Data Persistence

  • ext4 data volume per Machine on shared PD
  • Survives stop/restart (host-affinity)
  • Auto-backup before upgrades (.ext4.pre-upgrade)
  • Symlinked: /home/openclaw, /workspace

Capacity (n2-standard-16)

  • 8x Small (2 vCPU, 2GB) per host
  • 4x Medium (4 vCPU, 4GB) per host
  • 2x Large (8 vCPU, 8GB) per host

Metadata Service

Bridge-network service providing config, secrets, and LLM credentials to VMs with IP-based isolation.

How It Works

  • Runs on bridge IP 192.168.100.1
  • Each VM has unique bridge IP (192.168.100.X)
  • Requests authenticated by source IP + nonce
  • Serves assembled config.json5 per VM
  • Delivers decrypted secrets (memory-only)
  • Provides LLM API keys for LiteLLM proxy

Secret Management

Security Properties

  • Encrypted at rest — AES-256-GCM in database
  • Memory-only in VM — never written to VM disk
  • IP-isolated delivery — metadata service per-VM
  • Nonce authentication — prevents replay
  • Instant revocation — rotate encryption key, secrets invalidated
  • Destroyed on stop — VM memory freed, rootfs destroyed
08

Three-Layer Authentication

Defense in depth: edge identity, machine authorization, and internal service auth.

CF Access (Edge)

  • User identity verification
  • SSO via Google, GitHub, Email OTP
  • Sets CF_Authorization cookie
  • Zero-trust network access

Machine Token (VM)

  • HS256 JWT with 5-minute TTL
  • Scoped to specific access types
  • Validated by AuthProxy in each VM
  • Short-lived, auto-refreshed

Auth Proxy (Internal)

  • Per-request token validation
  • Routes to Gateway, Terminal, or ports
  • Internal-only gateway token
  • Runs inside VM on :8080

10

Capacity Scheduling

Bin-pack algorithm fills the fullest host first. Auto-scales hosts up on demand and down when idle.

Bin-Pack Algorithm

Selects the host with the most used resources that still has room. This maximizes density and minimizes wasted capacity.

Selection Criteria

  • Host status = ready
  • Available vCPUs ≥ requested
  • Available memory ≥ requested
  • Region preference match
  • ORDER BY used_memory DESC
  • FOR UPDATE SKIP LOCKED (race-free)

Auto-Scaling

Scale Up

  • No host has capacity → provision new GCP VM
  • Nested KVM enabled, Firecracker installed
  • Agent auto-starts, stages rootfs from GCS

Scale Down

  • Host idle >15 min → mark draining
  • No new VMs scheduled on draining hosts
  • Once empty → stop GCP VM
  • Data volumes persist on disk
