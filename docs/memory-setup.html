OpenClaw Memory Guide

How OpenClaw machines remember things — from the basics through to shared memory across machines.

Part 1 — Default Setup: How Memory Works

What happens out of the box with no configuration.

Notes Are Just Text Files

When OpenClaw saves something to memory, it writes a text file to disk. There are two kinds:

  • MEMORY.md — long-term notes (decisions, preferences, context that should persist).
  • memory/YYYY-MM-DD.md — daily session notes.

These are plain Markdown files. You can open them in any editor, and they'll survive restarts, updates, and migrations.

What Gets Indexed (and What Doesn't)

By default, only the memory files are searched — not everything on disk.

SEARCHED (memory files only): ├── MEMORY.md ← long-term notes └── memory/ ├── 2026-03-28.md ← daily session notes ├── 2026-03-29.md └── ... NOT SEARCHED: ├── source code (*.go, *.ts, *.py, etc.) ├── config files ├── documentation ├── images, PDFs, binaries └── anything else on the filesystem

Your workspace files — source code, configs, documentation — are not part of memory search. When the agent needs to look at those files, it reads them on-demand using tools (file read, grep, etc.), not through the memory system.

Why? Memory is for knowledge the agent has learned — decisions, context, preferences. Source code changes constantly and is better accessed directly when needed, rather than being pre-indexed into a search database that goes stale immediately.

Searching Memory (Default): Plain Text Retrieval

By default, there is no embedding model configured. When OpenClaw searches your memory, it reads the text files directly and matches against your query using simple text retrieval — looking for keywords and phrases that appear in your notes.

Notes (text files on disk) │ ▼ Text Search (keyword matching against file contents) │ ▼ Results: notes that contain matching words/phrases

This works, but it's limited — you can only find notes that contain the exact words you search for. If you wrote "deploying to production" but search for "shipping code to live servers," nothing comes back.

Default Limitations

  • Keyword-only search — only finds notes containing the exact words you search for. Can't understand meaning, synonyms, or related concepts.
  • Text only — no images, audio, or PDFs.
  • No recency awareness — a note from 6 months ago ranks the same as one from yesterday.
  • Each machine is isolated — if you have multiple machines, each one searches its own notes independently. No sharing.
  • External tools not included — Notion, Jira, Google Drive content isn't searched unless you explicitly export it and point OpenClaw at the files.

These limitations are what Part 2 solves — by adding an embedding model, search understands meaning, not just matching words.

Part 2 — Enhanced Setup: Better Search, Better Models

Why you'd upgrade, what each option does, and what it costs.

What Are Embeddings?

The default setup only matches exact words. Embeddings unlock meaning-based search.

An embedding model is a small AI whose only job is reading text and converting it into a list of numbers (called a vector) that captures its meaning. Two pieces of text about the same topic produce similar numbers — even if they use completely different words.

Example: You saved a note about "deploying to production." Later you search for "shipping code to live servers." With plain text search, nothing comes back — the words don't match. With embeddings, the vectors are nearly identical because the meaning is the same. The note is found.

How it works once enabled:

  1. When a note is saved, its text is sent to the embedding model → a vector is stored in a local database.
  2. When you search, your query is also embedded → you get a vector.
  3. The system finds stored vectors closest to your query vector → returns those notes.
Memory files (same as default — MEMORY.md + memory/*.md) + extraPaths (if configured — e.g. ~/data/notion, ~/data/jira) │ ▼ Embedding Model (cloud API — you choose the provider) │ reads text, outputs a vector (list of numbers) ▼ SQLite Database (one file, on the same machine) │ stores vectors alongside the original text ▼ Search: your query → embed → find closest vectors → return matching notes

What changes with embeddings: The same memory files are indexed, but now they're searchable by meaning instead of just keywords. You can also expand what's indexed by adding extraPaths — folders containing exported notes from Notion, Jira, Google Drive, etc. Source code and workspace files are still not indexed (the agent reads those on-demand with tools).

Embedding Providers

To enable embeddings, you need to choose a provider — a cloud service that runs the embedding model. You send it text, it sends back a vector. That's the entire interaction. The provider is the single biggest factor in search quality.

ProviderModelAccessCostQuality
Nebius mistral-embed API Key ~$0.01 / 1M tokens Very good
OpenAI text-embedding-3-small API Key ~$0.02 / 1M tokens Very good
Google Gemini embedding API Key ~$0.01 / 1M tokens Very good (supports images)
Voyage AI voyage-3-lite API Key ~$0.02 / 1M tokens Excellent for code
Access types explained:
  • API Key (pay-per-use) — Sign up with the provider, get an API key, pay only for what you use. No monthly commitment. All providers listed above work this way. You're charged per million tokens processed — typically fractions of a cent per note.
  • Platform / subscription — Some providers (e.g., OpenAI, Google) also offer embedding access through broader platform subscriptions (ChatGPT Plus, Google Cloud, etc.). If you already have one of these, you may already have access — check your plan's API limits.

For OCM, all providers use API key access. You paste the key into your config and OCM calls the provider's API directly. There are no subscriptions or platform accounts required beyond the API key itself.

What a provider does: You send it text, it sends back a vector. That's it. It's a single API call — fast, cheap, and stateless. The provider never stores your data.

Real-world cost: A 2,000-word note is about 3,000 tokens. At $0.02 per million tokens, indexing 1,000 notes costs about $0.06. Search queries are even cheaper (a few words each).

Hybrid Search (Vector + Keyword)

The problem: Pure vector search understands meaning but can miss exact terms. If you search for ERR_CONN_REFUSED or machine-7a3f, vector search might not find it because those aren't "meaningful" — they're identifiers.

The fix: Hybrid search runs two searches in parallel — one by meaning (vector) and one by exact keywords (called BM25, similar to how Google works). The results are merged, giving you the best of both worlds.

This runs locally, no extra API calls. The only cost is slightly more CPU during search.

How to enable

Add the hybrid block to your memorySearch.query config:

"query": {
  "hybrid": {
    "enabled": true,
    "vectorWeight": 0.7,   // how much weight to give meaning-based results (0–1)
    "textWeight": 0.3,     // how much weight to give keyword results (0–1)
    "candidateMultiplier": 4  // fetch 4x more candidates, then re-rank the merged results
  }
}

vectorWeight and textWeight control the blend. Start with 70/30 — this works well for most use cases. Increase textWeight if you frequently search for exact identifiers.

Temporal Decay (Recency Boost)

The problem: By default, a note from January ranks the same as one from yesterday. But usually, recent decisions are more relevant than old ones.

The fix: Temporal decay multiplies each result's relevance score by a freshness factor. You configure a "half-life" — e.g., 30 days means a note's score halves every month. Yesterday's note scores near 100%, a 2-month-old note scores around 25%.

No extra cost. Just a calculation applied after search.

How to enable

Add temporalDecay inside the hybrid block:

"temporalDecay": {
  "enabled": true,
  "halfLifeDays": 30   // score halves every 30 days — adjust to taste
}

Lower values (e.g., 7) aggressively favor recent notes. Higher values (e.g., 90) keep older notes competitive longer. 30 days is a good default.

Diversity Filtering (MMR)

The problem: If you wrote about the same topic 5 times, search returns 5 nearly identical results. The first is useful, the rest are noise.

The fix: MMR (Maximal Marginal Relevance) detects when results are too similar to each other and swaps duplicates for different-but-still-relevant notes. You get a broader picture instead of the same answer repeated.

No extra cost. Applied in post-processing.

How to enable

Add mmr inside the hybrid block:

"mmr": {
  "enabled": true,
  "lambda": 0.7   // 0 = maximum diversity, 1 = pure relevance. 0.7 is a good balance.
}

At lambda: 0.7, results are still ranked primarily by relevance but duplicates are filtered out. Lower it (e.g., 0.5) if you want more variety in results.

LanceDB (Better Local Storage)

The default uses SQLite to store vectors. LanceDB is a purpose-built alternative that's better at vector operations:

  • Columnar storage — vectors are stored in a format optimized for similarity search, so queries are faster on large collections.
  • No server needed — like SQLite, it's embedded (just a library, no separate process).
  • Scales better — handles hundreds of thousands of vectors without slowing down, where SQLite may struggle.
  • Built for AI workloads — native support for vector types, filtering, and hybrid search.

When to use it: If you have a large note collection (thousands of files or more), or if you want faster search. For small collections, SQLite is fine.

Cost: Free. Open source. Runs locally.

External Sources (Notion, Jira, Google Drive)

With embeddings enabled, you can expand what gets indexed beyond just the memory files. The extraPaths config tells OpenClaw to also index files from other folders — typically exports from external tools.

DEFAULT (always indexed): ├── MEMORY.md └── memory/*.md WITH extraPaths (also indexed when configured): ├── ~/data/notion/ ← exported Notion pages ├── ~/data/jira/ ← exported Jira tickets └── ~/data/gdrive/ ← exported Google Docs NEVER INDEXED (accessed on-demand by the agent via tools): ├── source code ├── config files └── everything else on disk

How to set it up:

  1. Export or sync content from your external tools to a local folder (e.g., ~/data/notion).
  2. Add those folders to memorySearch.extraPaths in the config.
  3. OpenClaw embeds and indexes those files alongside its own memory notes.
Be selective. Every file in extraPaths gets embedded — that means API calls to the embedding provider. If you dump 10,000 Jira tickets in there, that's 10,000 embedding calls. Only sync the content that's actually useful for the agent's work.

Enhanced Configuration Example

This turns on everything from Part 2 — better provider, hybrid search, recency, and diversity:

{
  "agents": {
    "defaults": {
      "memory": { "backend": "builtin", "citations": "auto" },
      "memorySearch": {
        "provider": "openai",
        "model": "mistral-embed",        // Nebius embedding model
        "extraPaths": ["~/data/notion"],  // external sources
        "cache": { "enabled": true, "maxEntries": 50000 },
        "query": {
          "hybrid": {
            "enabled": true,              // vector + keyword search
            "vectorWeight": 0.7,          // 70% meaning, 30% keywords
            "textWeight": 0.3,
            "candidateMultiplier": 4,
            "mmr": { "enabled": true, "lambda": 0.7 },          // diversity filter
            "temporalDecay": { "enabled": true, "halfLifeDays": 30 } // recency boost
          }
        },
        "sync": { "watch": true }         // auto-index new files
      }
    }
  },
  "models": {
    "providers": {
      "openai": {
        "apiKey": "YOUR_NEBIUS_API_KEY",
        "baseUrl": "https://api.nebius.ai/v1/"
      }
    }
  }
}

Part 3 — Shared Architecture: One Index, Many Machines

How to stop duplicating work and give every machine access to the same memory.

The Problem

With the default and enhanced setups, every machine runs its own indexing. If you have 10 machines:

  • The same notes are embedded 10 times — 10x the API cost.
  • Each machine has its own SQLite database — no shared knowledge.
  • A note saved on Machine A isn't searchable from Machine B.
  • New machines start with empty memory and have to re-index everything.

The Solution: Shared Vector Database + Indexer Agent

Replace the per-machine SQLite databases with a single shared vector database, and have one dedicated indexer agent do all the embedding work.

┌─────────────────────────────────────────────────────────┐ │ INDEXER AGENT (one instance) │ │ │ │ 1. Watches for new/changed notes (all sources) │ │ 2. Sends text to embedding model (one API call each) │ │ 3. Stores vectors in the shared vector database │ └────────────────────────┬────────────────────────────────┘ │ writes ▼ ┌─────────────────────┐ │ Shared Vector DB │ │ (Neon + pgvector, │ │ LanceDB, or │ │ Qdrant, etc.) │ └──────────┬──────────┘ │ reads ┌──────────────┼──────────────┐ ▼ ▼ ▼ ┌──────────┐ ┌──────────┐ ┌──────────┐ │Machine A │ │Machine B │ │Machine C │ ... │ │ │ │ │ │ │ search → │ │ search → │ │ search → │ │ embed │ │ embed │ │ embed │ │ query → │ │ query → │ │ query → │ │ find in │ │ find in │ │ find in │ │ shared DB│ │ shared DB│ │ shared DB│ └──────────┘ └──────────┘ └──────────┘

How it works:

  1. The indexer agent is a single process whose only job is watching for new or updated notes and embedding them. It writes vectors to the shared database. No other machine does indexing.
  2. When any machine searches memory, it embeds just the search query (one small API call) and queries the shared database for the closest vectors.
  3. All machines see the same results. A note saved anywhere is searchable everywhere.

Vector Database Options

OptionTypeWhy consider itTradeoff
Neon + pgvector Managed Postgres We already use Neon — just enable the extension. Zero new infrastructure. Not purpose-built for vectors; fine up to ~1M vectors.
LanceDB Embedded / serverless No server to run. Stores data as files (local or cloud storage like S3/GCS). Very fast. Can be shared via a common storage bucket. Newer project; less ecosystem tooling.
Qdrant Dedicated vector DB Purpose-built, very fast, good filtering. Free tier and self-host options. Another service to run/manage.
Pinecone Managed cloud Zero ops. Generous free tier. Vendor lock-in. Data leaves your infrastructure.
Recommended starting point: Neon + pgvector (already in our stack) or LanceDB backed by GCS (serverless, no database to manage, fast). Either avoids adding new infrastructure.

What the Indexer Agent Does

The indexer is a lightweight process — not a full OpenClaw machine. Its responsibilities:

  • Watch — monitors note directories for new or changed files (including extraPaths like Notion exports).
  • Chunk — splits large files into smaller pieces (e.g., per-section or per-paragraph) so search results are specific, not entire documents.
  • Embed — sends each chunk to the embedding model and gets back a vector.
  • Store — writes the vector + original text + metadata (source file, timestamp) to the shared database.
  • Deduplicate — tracks what's already indexed so unchanged files are skipped.

It can run on a schedule (e.g., every 5 minutes), on file-change events, or continuously.

Important: Model Consistency

All machines must use the same embedding model as the indexer. Different models produce different vectors — they're not compatible. If the indexer uses mistral-embed, every machine must also use mistral-embed for search queries. Mixing models will return garbage results.

Benefits

  • Index once, search everywhere — notes are embedded once by the indexer, not once per machine.
  • Shared knowledge — a note saved on any machine is instantly searchable from all others.
  • New machines start fully loaded — no bootstrapping or re-indexing. Connect to the shared DB and go.
  • Lower cost — embedding API calls scale with notes, not with machines. 10 machines cost the same as 1.
  • Centralized external sources — the indexer handles Notion/Jira/Drive exports once for everyone.

Example: Neon + pgvector Setup

-- Enable pgvector (run once)
CREATE EXTENSION IF NOT EXISTS vector;

-- Create the shared embeddings table
CREATE TABLE memory_embeddings (
    id          BIGSERIAL PRIMARY KEY,
    source_file TEXT NOT NULL,
    chunk_text  TEXT NOT NULL,
    embedding   vector(1024),       -- dimension depends on model
    created_at  TIMESTAMPTZ DEFAULT now(),
    updated_at  TIMESTAMPTZ DEFAULT now(),
    UNIQUE(source_file, chunk_text) -- avoid duplicates
);

-- Index for fast similarity search
CREATE INDEX ON memory_embeddings
    USING ivfflat (embedding vector_cosine_ops)
    WITH (lists = 100);

-- Index for hybrid keyword search
ALTER TABLE memory_embeddings ADD COLUMN tsv tsvector
    GENERATED ALWAYS AS (to_tsvector('english', chunk_text)) STORED;
CREATE INDEX ON memory_embeddings USING gin(tsv);

Example: LanceDB + GCS Setup

# LanceDB stores data as files — point it at a GCS bucket and all machines share it.
# No database server to manage.

import lancedb

# Indexer writes here
db = lancedb.connect("gs://ocm-memory/lancedb")
table = db.create_table("notes", data=[
    {"text": "chunk text here", "source": "MEMORY.md", "vector": [0.1, 0.2, ...]}
])

# Any machine reads from the same location
db = lancedb.connect("gs://ocm-memory/lancedb")
results = db.open_table("notes").search([0.1, 0.2, ...]).limit(10).to_list()

LanceDB handles vector indexing, filtering, and similarity search. The GCS bucket is the shared storage — no server process needed.
